# AI 辅助开发记录

这个项目从需求到测试都使用了 AI 编程工具（Claude Code / 这类命令行 Agent）参与，
但**分工是明确的**：AI 负责提速，人负责「决定什么是对的」。

## 我是怎么用的

| 环节 | AI 做什么 | 我做什么 |
| --- | --- | --- |
| 需求拆解 | 把「自然语言查数」拆成 schema 内省 / 提示词 / 护栏 / 执行 / 缓存 五块，并给出模块边界 | 砍掉不需要的部分（向量检索、多轮对话、前端），把范围压到能在一周内做完 |
| 代码骨架 | 生成 dataclass、FastAPI 路由、urllib 请求封装 | 重新设计 `QueryService.ask()` 的主流程与错误分类 |
| Prompt | 起草 System Prompt 与 3 条 few-shot | 逐条改规则：只输出 SQL、必须带 LIMIT、禁止 `SELECT *`、金额口径写死 |
| 测试 | 生成大部分用例骨架 | 补边界用例（注释绕过、`REPLACE()` 误杀、多语句、只读连接） |
| 文档 | 起草 README 结构与表格 | 用真实输出替换示例，删掉没跑通的说法 |

**关键原则：AI 写的 SQL 护栏、缓存键、只读连接这三处，我必须逐行看懂才允许合入。**
安全相关的代码不能「看起来能跑」就上线。

## 三个真实踩坑（都保留在提交历史里）

1. **离线替身取错了问题**
   提示词里的 few-shot 也写成「问题：xxx」，正则用 `re.search` 抓到的是第一条示例，
   导致离线模式永远返回同一个 SQL。改成按行匹配并取**最后一条**，才是本次真实问题。

2. **LIMIT 注入误伤聚合查询**
   AI 初版对所有缺 `LIMIT` 的 SQL 都追加 `LIMIT 200`，`SELECT COUNT(*)` 这种单行聚合也被加，
   输出多了一行无意义提示。改成「有聚合函数且没有 `GROUP BY` 时不注入」。
   这个改动同时暴露了测试缺口——原先没有覆盖聚合场景。

3. **Windows 路径没转义**
   `file:{path}?mode=ro` 在路径含空格或中文时会打开失败。
   用 `urllib.parse.quote(path, safe='/:')` 处理，同时保留盘符冒号。

## 不用 AI 的地方

- 安全边界（什么 SQL 允许执行、失败如何降级）由人决定，AI 只负责实现。
- 数据口径（销售额、客单价怎么算）由业务确认，AI 不知道你的口径。
- 性能数字一律实测，不采信 AI 估算。

## 给读代码的人

如果你在评审这个项目：先看 `src/nl2sql/guard.py`（安全边界），
再看 `src/nl2sql/service.py`（主流程），最后看 `tests/test_guard.py` 与
`tests/test_service.py`（怎么证明前两者是对的）。
